# v3.1 plan: close v3's loose ends, load the weights in parallel, harden the code

## Why

v3.0.0 shipped `Bands` (parallel matrix · vector without copies) and the answers to the launch feedback.
Three weak points remained: (1) on one thread v3 is ~12% slower than v2.1 and the README still shows v2's
numbers because nothing was measured on an idle machine; (2) loading GPT-2's weights takes 7-10 s against
~1 s for PyTorch, now the largest cost of the demo; (3) some guarantees are tests, not laws, and CI has
two deprecation deadlines (Node 20 actions; `ubuntu-latest` moves to Ubuntu 26 on 2026-10-19).
Renan chose items 1, 2 and 3. Item 4 (upstream) is only noted: **Renan opens the Bend issues/PRs himself
later**; the drafts stay in `docs/upstream/` and a line in `NOTES.md` says they are his to post.

## 0. Branch workflow (first, before any code)

From now on `main` only receives stable releases; day-to-day work happens on `devel`.

- `git switch -c devel` from the current `main` (v3.0.0) and `git push -u origin devel`. Every v3.1 commit
  goes to `devel`.
- CI (`.github/workflows/ci.yml`): `push: branches: [main, devel]`, so `devel` is checked on every push;
  pull requests stay checked as today.
- Release: when v3.1 is done and CI is green on `devel`, open a PR `devel` → `main` (`gh pr create`), merge it
  after its CI passes, then tag `v3.1.0` **on `main`** and create the release from that tag. `devel` keeps going
  from there.
- Write it down where agents read it: a short "Branches" rule in `CLAUDE.md` (work on `devel`; `main` only
  through a release PR; tags only on `main`), and the same in the contributing part of the README (one line).

## 1. Loose ends of v3

- **`Bands.matvec_l`** in `tensor-array/main.bend`: same as `Bands.matvec` but takes and returns lists
  (`x: List<&2, F32>` with c numbers → `BL<r, c>` with `y` as a list), skipping `bv_fin`'s
  `Mat.from_list` and the caller's `Mat.to_list`. Reuse `bmv`, `fill_list`, `cap_depth`. Keep the typed
  `Bands.matvec` as the default API; document `matvec_l` as the fast path whose length is checked by the
  law in item 3 (or by tests if that law turns out too expensive).
- **Cheaper concatenation:** leaves return their lists, nodes `List.append` the left one (O(r · depth)).
  Measure first; change only if it shows in the profile (e.g. return a tree of lists and flatten once).
- **Depth per matrix:** `get_bands(name, d, r, c)` in `demos/gpt2/fast.bend`; 2^5 for `wte` (4.5 vs 6.1 ms),
  2^4 for the layer matrices, chosen from `bench/results/mv_bands-2026-10-05.txt`.
- **Idle measurement:** before measuring, check `uptime` (load < 0.5) and `ps`. Renan's Android emulator and
  Gradle were running during v3; they are his processes, so ask him to close them rather than killing them.
  Re-run `bench/mv_bands.py` (with the typed and the list API) and GPT-2 v2.1 vs v3.1 alternated 5 times;
  then update `docs/media/numbers.json`, `make media`, the README tables and `demos/gpt2/BENCHMARK.md`.

## 2. Loading the weights in parallel

Profile from v3 (NOTES exp. 11): `wte` (38.6 M numbers) 1.9 s, the 12 layers (85 M numbers) 4.8 s, i.e.
~50 ns per number, spent turning 1 MB blocks into lists of bytes and then of `F32` (`demos/gpt2/load.bend`:
`f32s`, `f32_le`, `bitcast`). That work is pure, so it can run on every core.

- **Prototype first** (`.scratch/`): the guide says each computation started with `IO.fork` runs its pure
  code in parallel up to its next effect, and `IO.join` waits for it. Load the 12 layers with one
  `IO.fork` each (and `wte`, `wpe` in parallel with them), joining in order. Measure with 1 and 16 threads.
  If `IO.fork` does not overlap the conversions, try forking per band inside `load_tree`.
- **Then** apply to `load_layers` / `load_model` in `demos/gpt2/fast.bend`; keep the 1 MB blocks so the
  resident peak stays near ~1.5 GB (measure with `scripts/peak_rss.sh`).
- **Fewer conversions:** decode a block straight into the band's `Array` (bytes → `F32` → `Array.set`
  in one loop over the byte list) instead of building the `F32` list first: a `fill_bytes` in the demo
  next to `stream_exact`.
- Pass: ids and logits unchanged (`reference/test_gpt2.py`), load time and peak memory in
  `demos/gpt2/BENCHMARK.md` and `NOTES.md` (exp. 12), including a negative result if `IO.fork` does not help.

## 3. Robustness

- **A law for the list path:** `matvec_l` returns exactly r numbers. Needs: `lcols` adds `mleft + 1`
  numbers to `out` (induction on `mleft`, the values do not matter), `List.reverse` keeps the length, and
  `length_append` (in `bend-ml-nat-lemmas`; or a local copy, since `tensor-array` imports nothing today).
  If the proof gets expensive, record it in `NOTES.md` as open and keep the tests.
- **Checks at the boundary:** the GPT-2 loader compares `File.size` with `r*c*4` for every weight file and
  refuses with a clear message (the pattern of `Mat.of_list` / the merges-table check).
- **Property tests** in `reference/test_tensor_array.py`: more bands than rows (r = 3, d = 5: empty bands),
  r = 1 and c = 1, blocks of 1 number, blocks larger than the whole matrix, and `matvec_l` equal to
  `matvec` bit for bit.
- **A parallelism regression check** in `reference/check_all.py`, deterministic (no timing): compile a
  small `Bands.matvec` program to C (`bend X.bend -o x.c`) and require the join function of `bmv`
  (`FID_..._BMV_J..`). It fails if someone puts an erased parameter last again.
- **`make bench`**: runs `bench/mv_bands.py` and `scripts/compile_times.py` and writes dated files to
  `bench/results/` (not in CI: too noisy on a 4-vCPU runner).
- **CI** (`.github/workflows/ci.yml`): pin `runs-on: ubuntu-24.04`; move `actions/checkout`, `setup-python`,
  `cache`, `upload-artifact` to the majors that run on Node 24 (look up the current majors with
  `gh api repos/actions/<name>/releases/latest` before editing).
